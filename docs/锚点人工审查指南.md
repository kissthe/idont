# 锚点人工审查指南

版本 v0.1 · 2026-10-07 · 配套 `docs/锚点字段说明书.md` v0.1

---

## 1. 为什么要审，审什么

锚点是后续所有题目的真值来源：错一个锚点，由它生成的整组题的 gold 都会跟着错。所以 LLM 抽取完必须人工审。

**审查只回答两个问题：**

1. **抽出来的对不对（精确）**：每个锚点是否满足说明书里的 C1–C4，字段是否忠实于原文。
2. **有没有漏（召回）**：历史里还有哪些锚点没被抽出来。

**不审的内容：** 这个锚点能不能出 H 题、普通人会不会有同样的反应。这些是后续步骤的事。审查员不要因为"这个出不了好题"就拒绝一个合格的锚点，否则后续统计会失真。

---

## 2. 准备工作

- 审查前先通读说明书第 2、3 节，特别是 C1–C4 和"不算锚点的情况"。
- **对照原文审，不要只看抽取结果。** 每个锚点都要打开 `fact.turn_ids` 和 `meaning.turn_ids` 指向的原文，以及每一轮前后各 1–2 轮的上下文。建议用脚本把锚点和对应原文并排渲染出来，不要手动去源文件里翻找。
- 以一个对话、一个用户为单位，一次审完，便于发现重复和遗漏。

---

## 3. 逐个锚点的检查清单

按顺序检查。前面的问题不通过，后面的就不用看了。

| # | 检查什么 | 怎么查 | 不通过时 |
|---|---|---|---|
| Q1 | 证据是否真实 | 每个 `turn_id` 都存在、说话人是 `user_id`、内容确实在讲这件事 | 能删掉错的轮次就修改；全部不对就拒绝（R1） |
| Q2 | 是不是具体事件（C1） | 是一次具体经历或有来历的事物，而不是爱好、习惯、观点、计划 | 拒绝（R3） |
| Q3 | 意义是否由 u 明说（C2） | 在 `meaning.turn_ids` 的原文里找得到 u 亲口说的感受、行为变化或联结；不是抽取者推断的，也不是对方说的 | 原文另有明说的意义就改写；否则拒绝（R2 或 R6） |
| Q4 | 意义和事件是否连得上（C3） | 原文能看出感受是因这件事或这个事物而起 | 拒绝（R2） |
| Q5 | 线索是否合格（C4） | 具体、可感知、能在未来另一个场景里出现；不是抽象主题；用原文的限定写得足够具体 | 能改写就修改；找不到具体线索就拒绝（R4） |
| Q6 | 文字是否忠实 | `fact.text` 只写事实，`meaning.text` 只写感受；都没有加入原文之外的内容；没有把事实和意义写混 | 修改 |
| Q7 | 证据是否完整 | 原文里还有没有陈述同一事实或意义、却没被列进来的 u 的轮次（尤其是隔了很多 session 的）；有没有只是顺带提及、不该列的轮次 | 增删轮次后标为修改 |
| Q8 | 情绪是否正确 | `emotion` 与原文最终落脚的感受一致；只有行为变化时用 `not_expressed` | 修改 |
| Q9 | 是否重复或该拆分 | 同一线索被拆成了两个锚点（合并）；或者一个锚点塞了两个线索（拆分） | 修改，或对重复的那个拒绝（R5） |

### 边界情况

| 情况 | 处理 |
|---|---|
| 只说了"让我想起某人"，没有更多感受（conv-48 S01_T09："I also have a pendant that reminds me of my mother"） | 接受。"持续联结"本身就是意义；强弱留给后续判断 |
| 当时的情绪很强，但之后再没提起（例如一次经历后说"really scared"） | 接受。当时的情绪就是意义 |
| 配图描述和文字对不上（conv-42 S24_T04 的描述是"猫"，文字是毛绒玩具狗） | 以文字为准，不影响接受。在 `comment` 里注明，方便日后做多模态版本时处理 |
| 后来说"已经不在意了" | 接受，确认 `meaning.text` 写了这个变化并注明 session |
| 拿不准 | 标为 `unsure`，写明原因，交给第二个人裁决 |

## 4. 审查结论与记录格式

在每个事件里加一个 `review` 字段。LLM 输出的原始 6 个字段不要直接覆盖：修改时先把原值存进 `review.original`。

```json
"review": {
  "status": "revised",
  "reason": null,
  "reviewer": "yi",
  "comment": "补上 S29_T05；cue 改得更具体",
  "original": { "cue": "bench", "meaning": { "turn_ids": ["S01_T07", "S02_T13"] } }
}
```

| `status` | 含义 |
|---|---|
| `accepted` | 原样通过 |
| `revised` | 修改后通过；`original` 里记录被改字段的原值 |
| `rejected` | 拒绝；必须填 `reason` |
| `added` | 抽取漏掉、由审查员补充的锚点 |
| `unsure` | 待裁决；裁决后改成以上四种之一 |

**拒绝原因代码 `reason`：**

| 代码 | 含义 |
|---|---|
| R1 | 证据不存在或与内容不符 |
| R2 | 意义是推断的或泛泛的，或者和事件连不上 |
| R3 | 不是具体事件（爱好、习惯、观点、计划） |
| R4 | 没有具体可再现的线索 |
| R5 | 与其他锚点重复 |
| R6 | 意义或事实出自对方而非 u |

被拒绝的锚点**不要删除**。保留下来的拒绝记录，是改进抽取 prompt 的依据。

---

## 5. 召回检查：找漏掉的锚点

精确审完后，再看一遍历史，找没被抽出来的锚点。

- **pilot 阶段（conv-26、conv-30）全量做。** 逐个 session 浏览 u 的发言。LoCoMo 自带的 `session_summary`、`observation` 和 `event_summary` 可以帮忙快速定位，但最终以原文为准。
- **扩大规模后抽查约 20% 的对话。**
- 找到的漏抽锚点按说明书格式补上，`review.status` 写 `added`。

---

## 6. 一致性检查

- pilot 阶段选 1 个对话由两人独立审，计算两人"通过（accepted 加 revised）还是拒绝"判断的一致率和 Cohen's kappa。
- 有分歧的锚点逐个讨论。如果分歧来自规则不清，就修订说明书，更新版本号，并同步更新抽取 prompt。

---

## 7. 审完要统计什么

每批审完输出以下数字，用来决定是继续改 prompt 还是扩大规模：

| 指标 | 算法 |
|---|---|
| 精确率（宽松） | (accepted + revised) / LLM 抽出的总数 |
| 精确率（严格） | accepted / LLM 抽出的总数 |
| 召回率 | (accepted + revised) / (accepted + revised + added) |
| 拒绝原因分布 | 各 R 代码的数量，指出 prompt 该改哪里 |
| 修改字段分布 | `original` 里各字段出现的次数，指出哪个字段最常抽错 |

**建议门槛（pilot 后再校准）：** 宽松精确率 ≥ 70%、召回率 ≥ 60%，再扩大到全部对话；不到门槛就先改 prompt 重抽。
